## 1. NegRisk 마켓 기본 구조

NegRisk 마켓은 **상호 배타적인 k개의 아웃컴**을 가진 마켓입니다.
정확히 하나의 아웃컴만 승리하며, 승리 아웃컴의 YES 토큰은 $1로 정산됩니다.

**예시**: 2028 대선 (k=3)

| 아웃컴 | 설명 |
|---|---|
| a | 트럼프 승리 |
| b | 바이든 승리 |
| c | 기타 후보 승리 |

각 아웃컴에 대해 YES 토큰과 NO 토큰이 존재합니다.

---

## 2. 토큰 관계 규칙

NegRisk 마켓에서 성립하는 세 가지 핵심 등가 관계:

### 규칙 1: YES + NO Merge

```
YES_i + NO_i = 1 USDC
```

같은 아웃컴의 YES와 NO를 합치면 **즉시** 1 USDC로 교환됩니다.
결과에 관계없이 성립 (YES가 이기면 YES=$1+NO=$0, 지면 YES=$0+NO=$1).

### 규칙 2: 완전 YES 세트

```
YES_a + YES_b + ... + YES_k = 1 USDC
```

모든 아웃컴의 YES를 1개씩 모으면 1 USDC. 정확히 하나가 승리하므로 항상 성립.

### 규칙 3: NegRisk 변환 (핵심)

```
NO_i = YES_j (for all j ≠ i)
```

**NO 토큰 1개는 "나머지 모든 아웃컴의 YES 각 1개"와 같다.**

i가 지면(NO_i 승리) → 나머지 중 하나가 이김 → 해당 YES가 $1 → 동일한 가치.

이 등가 관계를 스마트 컨트랙트로 실행하는 것이 **NegRisk 어댑터**입니다:

```
NO_i  →  {YES_j : j ≠ i}       (1개의 NO → k-1개의 YES, 정방향만 지원)
```

> **참고**: 수학적으로는 `{YES_j : j ≠ i} → NO_i` (역방향)도 등가이지만,
> Polymarket NegRisk 어댑터 컨트랙트는 **`NO → YES` 정방향 변환만** 지원합니다.
> 역방향 변환 함수는 구현되어 있지 않습니다.

## 3. Strategy A: Buy All YES

### 아웃컴 분류 (3-bucket)

모든 아웃컴을 아래 3가지로 분류합니다:

| 분류 | 조건 | 의미 |
|------|------|------|
| **Active** | YES_ask ≥ threshold (1¢) | 가격 존재, 거래 가능 |
| **Resolved** | YES_ask 존재 & < threshold | 현실에서 결정됨, 가격 0.x¢ 수렴 |
| **Illiquid** | YES_ask = None (호가창 없음) | 가격 불명, 가치 불명 |

설정 키: `NEGRISK_YES_RESOLVED_THRESHOLD` (기본 $0.01 = 1¢)

**핵심 구분**:
- **Resolved**: 이미 결정된 아웃컴 → 안전하게 제외 가능
- **Illiquid**: 호가창이 비어 있을 뿐, 실제 가치가 높을 수 있음 → 제외 불가

Illiquid 아웃컴이 하나라도 있으면 YES_ARB를 **거부**합니다.
(사이트 표시가 59¢인데 호가창이 비어 ask=None이면, 이를 0으로 간주하면
거짓 차익 기회가 감지됩니다.)

### 조건

```
1. illiquid 아웃컴 = 0  (모든 아웃컴에 YES ask 존재)
2. Σ p_YES_active < 1   (YES_ask ≥ 1¢인 활성 아웃컴만 합산)
3. active 아웃컴 ≥ 2
```

> Illiquid 없이, 활성 아웃컴의 YES 가격 합이 1달러 미만일 때 차익 발생

### 수식

```
Cost    = j × Σ p_YES_i          (모든 YES를 j개씩 구매)
Return  = j × 1 USDC             (완전 세트 merge 또는 정산)
Profit  = j × (1 - Σ p_YES_i) - fees
```

### 실행 흐름

```
┌─────────────────────────────────────────────────┐
│  Step 1: 각 아웃컴의 YES를 j개씩 시장가 매수       │
│          Cost = j × (p_YES_a + p_YES_b + p_YES_c)│
│                                                   │
│  Step 2: 완전 YES 세트 merge (CTF)                │
│          j × {YES_a, YES_b, YES_c} → j USDC      │
│          또는 만기일까지 보유 후 정산               │
│                                                   │
│  Profit = j × 1 USDC - Cost - fees               │
└─────────────────────────────────────────────────┘
```

### 예시 (k=3, j=100)

| 아웃컴 | YES 가격 | 매수 비용 (j=100) |
|---|---|---|
| a (트럼프) | $0.45 | $45.00 |
| b (바이든) | $0.30 | $30.00 |
| c (기타) | $0.15 | $15.00 |
| **합계** | **$0.90** | **$90.00** |

```
Return  = 100 × $1.00 = $100.00
Profit  = $100.00 - $90.00 - fees = ~$10.00
ROI     = 11.1%
```

### Liquidity Hold 방어 조건

YES_ARB는 NO_CONVERT_ARB와 달리 즉시 청산 경로가 없습니다.
완전 세트 merge가 불가능하면 만기까지 자본이 잠기므로, 두 가지 추가 조건을 적용합니다:

```
조건 (1): margin ≥ yes_arb_min_margin (기본 0.03 = 3센트)
           → 마진이 너무 작으면 자본 잠김 대비 수익이 불충분

조건 (2): end_date ≤ now + yes_arb_max_expiry_days (기본 30일)
           → 만기가 너무 먼 이벤트는 자본 회전 비효율
           → end_date가 없는 이벤트도 거부
```

설정 키: `NEGRISK_YES_ARB_MAX_EXPIRY_DAYS`, `NEGRISK_YES_ARB_MIN_MARGIN`

### 특성

- **장점**: 단순, 온체인 비용 낮음 (구매만)
- **단점**: 완전 세트 merge가 불가능하면 만기까지 자본 잠김 → 위 방어 조건으로 완화
- **기회 빈도**: 낮음 (합 < 1이 되는 경우가 드묾)

## 4. Strategy B: Buy All NO + Convert

### 조건

```
Σ p_NO_active < k_active - 1
```

> **활성** 아웃컴의 NO 가격 합이 (활성 아웃컴 수 - 1) 미만일 때 차익 발생.
> Resolved(가격 0 또는 None) 아웃컴은 자동 제외됨.

### Resolved Outcome 제외 로직

날씨 마켓 등에서 이벤트가 아직 종료되지 않았지만 일부 아웃컴이 이미 결정된 경우
(예: "3월 시애틀 강수량 > 5인치?" — 이미 초과됨), 해당 아웃컴의 YES ≈ $1, NO ≈ $0
으로 수렴하여 호가창에 유동성이 사라집니다.

이런 "resolved" 아웃컴을 계산에 포함하면:
- `no_price_sum()`이 None을 반환 (가격 없음) → 이벤트 전체가 skip됨
- 또는 0을 포함해서 합산하면 부정확한 threshold 비교가 됨

**해결**: `k_active`(활성 아웃컴만 카운트)를 기준으로 모든 수식을 재계산:

```
k_active = |{i : p_NO_i ≠ None AND p_NO_i > 0}|
Threshold = k_active - 1
```

수학적으로, k_active개의 NO만 매수/변환하면:
- k_active - 1 번 변환 → k_active - 1개의 완전 YES 세트 → k_active - 1 USDC
- 수익은 정확히 j × (k_active - 1 - Σ p_NO_active)

### 왜 k-1인가?

1개의 NO는 (k-1)개의 YES로 변환됩니다.
k개의 NO를 전부 변환하면 각 아웃컴의 YES가 (k-1)개씩 생기므로:

```
k_active개 NO 전부 변환 → (k_active-1)개 완전 YES 세트 → (k_active-1) USDC
```

### 수식

```
Cost    = j × Σ p_NO_active         (활성 아웃컴 NO만 j개씩 구매)
Return  = j × (k_active-1) USDC     (변환 + merge)
Profit  = j × ((k_active-1) - Σ p_NO_active) - fees
```

### 최적화된 실행: "하나 남기기"

전부 변환하는 대신, **하나의 NO를 남기고 나머지만 변환**하면 즉시 청산이 가능합니다.

#### 단계별 예시 (k=3, j=1)

**Step 1: 구매**

| 구매 | 가격 |
|---|---|
| a_NO × 1 | $0.79 |
| b_NO × 1 | $0.67 |
| c_NO × 1 | $0.50 |
| **합계** | **$1.96** |

조건: $1.96 < k-1 = 2 ✓

> 이때 각 아웃컴의 YES 매도호가는 0.22 / 0.34 / 0.51이라 마켓별 YES+NO는 모두 1.01입니다. 단일 마켓 기준(karb의 Pure Arb)으로는 기회가 보이지 않습니다.

**Step 2: a_NO 유지, b_NO와 c_NO만 NegRisk 변환**

```
b_NO → YES_a + YES_c    (NO_b는 "b 아닌 것들의 YES"와 같다)
c_NO → YES_a + YES_b    (NO_c는 "c 아닌 것들의 YES"와 같다)
```

**Step 3: 변환 후 보유 상태**

| 토큰 | 수량 | 출처 |
|---|---|---|
| a_NO | 1 | 원래 구매 (유지) |
| a_YES | **2** | b_NO 변환(1) + c_NO 변환(1) |
| b_YES | 1 | c_NO 변환(1) |
| c_YES | 1 | b_NO 변환(1) |

**Step 4: 즉시 청산 (2경로 동시 실행)**

```
경로 A:  a_NO(1) + a_YES(1) → merge → 1 USDC    ← 즉시! 재투입 가능
경로 B:  a_YES(1) + b_YES(1) + c_YES(1) → 완전 세트 merge → 1 USDC
                                                    ──────────
                                              합계: 2 USDC (= k-1)
```

**수익 계산:**

```
Return  = 2 USDC
Cost    = 1.96 USDC
Profit  = 2 - 1.96 - fees = ~$0.04
ROI     = 2.04%
```

### 일반화 (k개 아웃컴, j개 매수)

"하나 남기기"로 최적 청산할 때, 남길 NO를 아웃컴 `t`로 선택하면:

```
1. 구매: 모든 i에 대해 NO_i × j개  (비용 = j × Σ p_NO_i)

2. 변환: i ≠ t인 모든 NO_i를 NegRisk 변환
   NO_i → {YES_m : m ≠ i}  (각 변환에서 k-1개 YES 생성)

3. 변환 결과:
   - t_NO:  j개 (유지)
   - t_YES: j × (k-1)개 (다른 모든 NO가 변환될 때 YES_t 하나씩 생성)
   - 기타 YES_m: j × (k-2) + j = j × (k-1)개

4. 즉시 청산:
   경로 A: t_NO(j) + t_YES(j) → merge → j USDC
   경로 B: 남은 YES로 완전 세트 j×(k-2)개 merge → j×(k-2) USDC
   합계: j × (k-1) USDC
```

### "하나 남기기" 타겟 선택

어떤 NO를 남길 것인가? → **가장 비싼 NO를 남기는 것이 최적**

남기는 NO의 가격은 결과에 영향 없음 (어차피 merge로 1 USDC가 됨).
하지만 변환 수수료(가스비)가 변환 횟수에 비례하므로, 변환 횟수를 최소화하기 위해
가장 비싼 NO(= 가장 가능성 낮은 아웃컴의 NO)를 남기면 됩니다.

실질적으로는 **가스비 최적화**보다 **유동성(오더북 깊이)**으로 타겟을 선택하는 것이 더 중요합니다.

### 특성

- **장점**: 즉시 청산 가능, 자본 회전 빠름, 기회 빈도 높음
- **단점**: 온체인 비용 높음 (변환 + merge 트랜잭션), 실행 복잡
- **기회 빈도**: Strategy A보다 높음 (k-1 기준이 더 넉넉)

## 5. karb Pure Arb vs Polly-Bot NegRisk 전략

Polly-Bot은 karb 오픈소스 봇을 기반으로 합니다.
karb는 **Pure Arb**(단일 마켓 차익거래)만 수행하며, Polly-Bot이 **NegRisk 전략을 추가**한 것입니다.

### Pure Arb란?

하나의 마켓에서 YES + NO를 동시에 사서, 합산 비용이 $1 미만이면 확정 수익:

```
조건: p_YES_ask + p_NO_ask < 1
수익: 1 - (p_YES_ask + p_NO_ask)
```

예시: YES=$0.45, NO=$0.50이면 → 비용 $0.95, 수익 $0.05 (5.3%)
결과에 관계없이 YES+NO=1이므로 확정 수익.

### 3가지 전략 비교

| 항목 | Pure Arb (karb 기존) | YES_ARB (Polly-Bot) | NO_CONVERT_ARB (Polly-Bot) |
|---|---|---|---|
| **분석 단위** | 마켓 1개 | 이벤트 내 k개 마켓 전체 | 이벤트 내 k개 마켓 전체 |
| **수익 조건** | p_YES + p_NO < 1 | Σ p_YES < 1 | Σ p_NO < k-1 |
| **수익 공식** | 1 - (YES+NO) | j × (1 - Σ p_YES) | j × (k-1 - Σ p_NO) |
| **NegRisk 변환** | 불필요 | 불필요 | 필요 (NO→YES 변환 + merge) |
| **"하나 남기기" 최적화** | 해당 없음 | 해당 없음 | 즉시 청산 경로 |
| **j 계산** | 단순 (오더북 2개) | 오더북 k개의 최솟값 | 오더북 k개의 최솟값 |
| **청산 방식** | 만기 정산 | 완전 세트 merge / 만기 | NO+YES merge + 완전 세트 merge (즉시) |
| **자본 회전** | 느림 | 느림 | 빠름 |
| **온체인 비용** | 낮음 | 낮음 | 높음 (변환 + merge) |
| **실행 복잡도** | Low | Low | High |
| **기회 빈도** | 매우 드묾 | 낮음 | 높음 |
| **슬리피지 시뮬레이션** | 기본적 | 동적 안전마진 | 동적 안전마진 |
| **추천/스코어링** | 없음 | ROI/유동성/실행가능성 | ROI/유동성/실행가능성 |
| **UI** | HTML 대시보드 | React 탭 + 계산 상세 | React 탭 + 변환 시뮬레이터 |
| **최적 상황** | 가격 비효율 순간 포착 | 만기 임박 + 가격 괴리 | 아웃컴 많은(k≥3) 활발한 마켓 |

### 핵심 차이 요약

- **karb (Pure Arb)**: "이 마켓 하나의 YES+NO가 $1보다 싸다" → 매수
- **Polly-Bot (NegRisk)**: "이 이벤트의 아웃컴 전체를 조합하면 차익이 난다" → 변환 + merge

Pure Arb는 단일 마켓의 순간적 가격 비효율을 잡는 것이고,
NegRisk 전략은 여러 아웃컴 간의 구조적 가격 불일치를 활용하는 것입니다.
Polly-Bot에서는 세 전략이 **병렬로 동작**합니다.

## 6. YES_ARB vs NO_CONVERT_ARB 비교

| 항목 | Strategy A (Buy All YES) | Strategy B (Buy All NO + Convert) |
|---|---|---|
| **전략 코드** | `YES_ARB` | `NO_CONVERT_ARB` |
| **수익 조건** | Σ p_YES < 1 | Σ p_NO < k-1 |
| **수익 공식** | j × (1 - Σ p_YES) | j × (k-1 - Σ p_NO) |
| **청산 방식** | 완전 세트 merge / 만기 정산 | NO+YES merge + 완전 세트 merge (즉시) |
| **자본 회전** | 느림 | 빠름 |
| **온체인 비용** | 낮음 | 높음 (변환 + merge) |
| **실행 복잡도** | Low | High |
| **기회 빈도** | 낮음 | 높음 |
| **최적 상황** | 만기 임박 + 가격 괴리 큰 마켓 | 아웃컴 많은(k≥3) 활발한 마켓 |

## 7. 매수 수량 결정 (j)

j는 **모든 아웃컴에서 동일 수량**을 매수해야 하므로, 가장 유동성이 낮은 아웃컴이 병목입니다.

### 기본 공식

```
j = min(available_depth_at_target_price[i] for i in all_outcomes) × depth_ratio
```

`depth_ratio`(기본값 0.5 = 50%)를 적용하여 최소 오더북 깊이의 일부만 사용합니다.
전량 소화를 시도하면 하위 가격 레벨까지 밀리며 슬리피지가 급증하므로,
상위 물량만 소화하여 슬리피지를 최소화합니다.

### 오더북 깊이 기반 계산

각 아웃컴의 오더북에서 **목표 가격까지의 누적 물량**을 계산:

```
아웃컴 a (NO):  $0.79에 500개, $0.80에 300개, $0.81에 200개 → $0.81까지 1000개
아웃컴 b (NO):  $0.67에 200개, $0.68에 150개 → $0.68까지 350개
아웃컴 c (NO):  $0.50에 800개 → $0.50까지 800개

min_depth = min(1000, 350, 800) = 350
j_max = 350 × 0.5 = 175   (depth_ratio=0.5 적용)
```

> **왜 100%를 사용하지 않는가?**
> 1. best ask 물량을 전부 소화하면 다음 가격 레벨로 밀려 실효 단가가 크게 올라감
> 2. 다른 봇이 동시에 같은 기회를 노리므로 전량 확보가 보장되지 않음
> 3. 50% 수준이면 슬리피지를 억제하면서도 충분한 수량을 확보할 수 있음

### 실효 가격 (슬리피지 포함)

j개를 시장가로 매수할 때 실제 평균 단가:

```
effective_price_i(j) = Σ(price_level × quantity_at_level) / j
                       (오더북을 j개 채울 때까지 위로 소화)
```

## 8. 슬리피지 & 안전마진

### 안전마진 (a)

실제 실행 시 가격이 밀리므로 안전마진을 적용:

```
Strategy A:  Σ p_YES < 1 - a
Strategy B:  Σ p_NO  < (k-1) - a
```

### a의 결정 방법

**방법 1: 고정값**

```
a = 0.02  (2센트 마진)
```

**방법 2: 동적 계산 (권장)**

```
a = estimated_slippage(j) + gas_fees + safety_buffer

estimated_slippage(j) = Σ (effective_price_i(j) - best_ask_i)
gas_fees = 변환 트랜잭션 수 × 평균 가스비
safety_buffer = 0.005 (0.5센트 고정)
```

### 경쟁 상황 고려

다른 봇이 같은 기회를 선점할 수 있으므로:
- 실행 직전에 오더북 재확인
- 부분 체결 대비 (j개 중 일부만 체결될 경우 롤백 전략)

## 9. Partial Fill 대응 전략: Retry-then-Hold

NegRisk 전략은 k개의 FOK 주문을 병렬로 발송합니다.
k가 클수록 일부 주문이 유동성 부족으로 실패할 확률이 높아지며,
이를 "partial fill"이라 합니다.

### 세 가지 대응 전략 비교

k-outcome 이벤트, j shares, m개 체결 / (k-m)개 실패:

| 전략 | 기대 수익 (EV) | 특성 |
|---|---|---|
| **Hold** (그냥 보유) | ≈ 0 (효율적 시장) | 추가 비용 없음, 분산 높음 |
| **Unwind** (손절 매도) | -j × Σ spread (확정 손실) | m개 전부 매도, 항상 열등 |
| **Retry + Complete Set** | 원래 차익 수익 × P(재시도 성공) | **최선** |

### 왜 NegRisk에서는 Retry가 PureArb보다 유리한가

PureArb partial fill은 **같은 마켓**의 반대편(YES↔NO)이 실패한 것이므로,
같은 마켓에서 재시도해도 성공 확률이 낮습니다.

NegRisk는 k개의 **서로 다른 마켓**에서 같은 방향을 매수합니다.
마켓 3이 실패해도 마켓 1, 2의 유동성과는 무관합니다.
FOK 실패 = "이 순간에 이 가격에 물량이 부족했다"이며,
200ms 후 마켓메이커가 호가를 갱신하면 동일 가격에 재시도 성공이 가능합니다.

### Retry-then-Hold 실행 흐름

```
1. k개 FOK 주문 병렬 발송
   ├── 모두 체결 → Complete Set Merge → 수익 확정 ✓
   └── 일부 실패 ↓

2. Phantom Fill 감지
   - exception으로 실패 처리된 주문의 실제 상태를 API로 확인
   - 이미 체결된 주문이 있으면 "filled"로 정정

3. 수익성 재확인
   - 현재 가격 기준으로 나머지를 매수해도 수익인지 계산
   - 수익 없음 → Hold (아래 6번으로)

4. Retry #1 (200ms 대기)
   - 실패 주문만 현재 best_ask 가격으로 재발송 (FOK)
   ├── 모두 체결 → Complete Set Merge ✓
   └── 일부 실패 → 수익성 재확인 ↓

5. Retry #2 (500ms 대기)
   - 동일 로직으로 최종 재시도
   ├── 모두 체결 → Complete Set Merge ✓
   └── 일부 실패 ↓

6. Hold: 체결된 포지션 보유 (EV ≈ 0)
   - partial_positions에 보유 내역 기록
   - 추가 손실 없이 시장 정산 대기
   - status = "partial_hold"
```

### 핵심 규칙

1. **최대 2회 재시도** (200ms, 500ms) — 가격 변동 위험 제한
2. **매 재시도 전 수익성 재확인** — 차익이 사라졌으면 즉시 Hold
3. **현재 best_ask 반영** — 고정 가격이 아닌 최신 호가 사용
4. **Phantom Fill 감지** — 네트워크 오류로 실패 처리된 주문의 실제 체결 확인
5. **Unwind 절대 안 함** — 수학적으로 항상 열등 (확정 손실 vs EV≈0)

### 수학적 근거

**Hold EV**:
```
비용 = j × Σ_{filled} p_i
P(당첨) = Σ_{filled} p_i   (NegRisk: 정확히 1개만 YES 정산)
E[payout] = j × Σ_{filled} p_i = 비용
E[profit] = 0
```

**Unwind EV**:
```
매도 수익 = j × Σ_{filled} (p_i - spread_i)
E[profit] = -j × Σ_{filled} spread_i < 0    (확정 손실)
```

**Retry + Complete EV**:
```
P = P(재시도 성공)
E[profit] = P × (원래 차익 수익) + (1-P) × 0
         = P × j × (1 - Σ p_i)    (YES_ARB의 경우)
```

P > 0이면 Retry가 항상 Hold보다 우월하고, Hold는 항상 Unwind보다 우월합니다.

### 결과 경로 (NegRisk 전용)

| 경로 | 상태 | 설명 |
|---|---|---|
| 전체 체결 | `filled` | k개 전부 체결 → merge → 확정 수익 |
| 재시도 후 완성 | `filled` | partial → retry 성공 → merge → 수익 (약간 감소 가능) |
| 양방 실패 | `failed` | FOK 전부 Kill — 포지션 없음, 손실 없음 |
| 부분 보유 | `partial_hold` | retry 실패 → 체결 포지션 Hold (EV≈0) |
| 거부 | `rejected` | 수익성 미달 — 주문 미발송 |
| 시뮬레이션 | `simulated` | DRY_RUN 모드 |
